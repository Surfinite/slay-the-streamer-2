# v0.113.0 compatibility: findings, plan of action, test plan

**Game update**: Beta v0.111.0 → v0.113.0 (released 2026-11-12, installed 2026-11-13). There was no v0.112.
**Branches to support**: default/stable **v0.107.1** (build of 2026-06-19, unchanged) and beta **v0.113.0**. MegaCrit has said the default branch will move to v0.111.0 content, with no date; v0.111.0 is covered by the automated checker only, not by play-testing.
**Status**: audit written 2026-11-13. Work items W1 to W10 and W12 are implemented (commits `v113-compat/1` to `/10`, same day); the in-game test plan in section 5 has not been run yet. W11 waits on test 5.2. Sections 1 to 3 describe the game and the published v0.4.3 as found, before the fixes.

Compiling clean and still being broken is the point: every break is in something the compiler can't see (Harmony targets bound by name or by exact parameter list, private fields looked up by string, a constructor whose optional parameter changed the compiled signature, vanilla behaviour that moved).

### The published v0.4.3 on beta today

Harmony registers patch classes in assembly order and stops at the first one that throws. On v0.113.0 that is `RandomCharacterResolvePatch`. The result, read off the published DLL's type order:

- **Registered and live**: settings panel, chest and elite relic choices, act-variant vote, Pael exclusion, Ancient vote, the card vote's `SelectCard` prefix, choose-a-card remove-one, event-option text, loc text, top-bar map guard, Doomed icon, relic disables, Talisman rework, Custom Mode Random button.
- **Never registered**: boss vote, Random resolve and reveal, and every nested patch class: the whole skip gate, the card vote's Skip/Reroll guards, all four origin tags, unskippable rewards, voter names, sealed-Neow text.

Two of the live ones are themselves broken on v0.113.0:

- **Elite relic choice** calls a `RelicReward` constructor whose compiled signature no longer exists. The postfix runs on every combat's reward generation and fails before its own `try` block, even with Relic choices set to 1. Expected symptom: reward generation throws after a fight. Confirmed by the checker; not yet seen in-game (today's run was abandoned before a combat ended).
- **Chest relic choice** reads a private field that was renamed, so it fails the first time a chest opens.

**Do not stream on beta with v0.4.3.** Stable-branch users are unaffected.

All verified against the decompiled source for v0.107.1, v0.111.0 and v0.113.0.

**Game-mode enum hazard** (nothing in the mod trips it today, but every new mode check must respect it): `GameMode` was `None, Standard, Daily, Custom` and is now `None, Standard, Daily, Dread, Blitz`. Value 3 means Custom on stable and Dread on beta. Any mode check must compare the enum's **name** (`GameMode.ToString() == "Dread"`), never a compiled constant.

## 6. The reference checker

A new tool that reads the mod DLL's metadata and checks every reference into `sts2.dll` against a given game DLL, plus Harmony targets, patch-parameter names and literal `AccessTools` lookups. It found H3 and H9, which no source reading had caught, and reproduced H1, H2 and H4. It runs in seconds and never loads the game.

- Lives in `tools/refcheck/`; run with `pwsh -File tools\refcheck\run.ps1` after `build.ps1`. The reports from this audit are in `decompiled/refcheck/` (gitignored).
- Archived game DLLs: `decompiled/dll-archive/sts2-v0.111.0.dll`, `sts2-v0.113.0.dll`. `build.ps1` now archives the installed game's DLL there by version, so the first build on the default branch (test 3.0) adds v0.107.1. Until then v0.107.1 is checked textually against its decompile tree.
- Known gaps: it doesn't see `FieldRefAccess<T,F>("name")` lookups (it missed H5), it can't see behaviour changes (H6, H7, H8, every row in section 3), and it doesn't compare enum constant values.

Validated against two other Workshop mods as controls. BaseLib (built for v0.113.0) passes on v0.113.0 and fails on v0.111.0 exactly where expected. StS1 Boss Ancients (built for an older game) passes on v0.111.0 and fails on v0.113.0, including one gap that stops it loading; that gap was confirmed in the decompiled source.
